Clawke 版本兼容与客户端自动升级设计

核心决策：客户端和当前服务端的 major.minor 必须一致；patch 差异只提示风险并允许继续，只有兼容线变化才阻断主流程。

核心决策

运行兼容优先

客户端启动后先检查本地 Server 版本。Client 与 Server 的 major.minor 不一致时，不进入聊天主流程。

兼容线强约束

服务端做判断

客户端只上报版本、build、平台、架构、安装渠道。兼容判断、GitHub latest、下载资产匹配都由 Server 负责。

瘦客户端

clawke update 边界不变

clawke update 只升级 Server/Gateway。客户端升级由客户端 UI 引导，按平台触发安装流程。

职责清晰

版本规则

Client ↔ 当前 Server

major.minor 必须一致；patch 差异只提示“可能不兼容或出现异常”。build number 不参与运行兼容。

组合 结果
Client 3.8.1 + Server 3.8.1 兼容
Client 3.8.1 + Server 3.8.2 可选提示，知道了可关闭
Client 3.9.0 + Server 3.8.1 阻断，先升级服务端
Client 3.8.1+84 + Server 3.8.1 兼容

Client ↔ GitHub Latest

按 ICU 风格判断升级级别。

比较 结果
major.minor 不同 强制升级
major.minor 相同，patch/build 不同 可选升级
完全相同 无需提示
顺序：

当前 Client/Server 一致后，如果 GitHub 有新版本，提示先运行 clawke update 升级服务端，再升级客户端。

API 契约

复用现有 WebSocket check_update，通过 version_check_protocol: 2 启用新协议。旧客户端继续走旧结构。

请求

{
  "event_type": "check_update",
  "data": {
    "version_check_protocol": 2,
    "app_version": "3.8.1",
    "app_build": "83",
    "platform": "macos",
    "arch": "arm64",
    "install_channel": "direct",
    "protocol_version": "cup_v2"
  }
}

响应

{
  "payload_type": "system_status",
  "status": "version_check_result",
  "action": "recommended_client_update",
  "compatibility": {
    "compatible": true,
    "warning": "patch_mismatch",
    "client_version": "3.8.1",
    "server_version": "3.8.2",
    "required_client_version": "3.8.2"
  },
  "presentation": {
    "title": "建议升级客户端",
    "message": "当前服务端版本为 3.8.2，客户端版本为 3.8.1。版本不完全一致，可能不兼容或出现异常；建议升级客户端到 3.8.2。",
    "primary_label": "立即升级",
    "secondary_label": "知道了"
  },
  "installer": {
    "method": "download_and_install",
    "url": "https://github.com/.../Clawke-3.8.2.apk",
    "sha256": ""
  }
}

客户端职责

上报版本和平台，展示服务端返回的文案，执行安装动作。

服务端职责

读取 Server 版本，查 GitHub Release，匹配资产，生成 action。

兼容策略

旧客户端不带 v2 字段时保持旧响应，避免破坏已发布版本。

Action 语义

Action 含义 UI 行为
ok Client/Server 一致，没有需要提示的新版本。 不提示。
recommended_client_update Server 和 Client 同 major.minor，但 Server patch 更新。 可选提示，显示“知道了”和“立即升级”。
recommended_server_update Server 和 Client 同 major.minor，但 Client patch 更新。 可选提示，显示“知道了”和“重新检查”。
required_client_update Server 和 Client 的 major.minor 不同，且 Client 较旧。 阻断主流程，只允许升级客户端。
required_server_update Server 和 Client 的 major.minor 不同，且 Server 较旧。 阻断主流程，提示运行 clawke update。
optional_server_then_client_update 当前版本匹配，GitHub 有同 major.minor 的 patch 更新。 可关闭提示，建议先升级服务端再升级客户端。
required_server_then_client_update 当前版本匹配，但 GitHub latest 的 major.minor 更高。 强制提示先升级服务端，再升级客户端。
check_failed GitHub 查询失败，但本地兼容检查已完成。 不阻断使用，只提示无法确认最新版本。

平台安装策略

Android

下载 APK 到应用私有外部目录，校验后通过 MethodChannel 调 Android 系统安装器。

参考 rc-world 思路

iOS

不做应用内安装，只跳 App Store 或 TestFlight。

平台限制

macOS direct

下载 DMG/ZIP，校验后用系统打开。App Store 渠道跳商店。

后续可评估 Sparkle

Windows

下载 EXE 或 MSIX，校验后打开安装器。

系统安装流程

Linux

优先 AppImage：下载、校验、chmod +x 后打开。deb/rpm 用 xdg-open。

不做 sudo 静默安装

资产命名

发布包命名必须稳定，便于服务端按平台和架构匹配。

可自动选择

流程边界

1

WebSocket 连接成功

客户端先发送 check_update v2，不要直接进入主业务交互。

2

服务端判断本地兼容

Client/Server 的 major.minor 不一致时立即返回阻断 action；只有 patch 差异时返回可选提示。

3

再判断 GitHub 最新版本

本地匹配后，才判断是否需要提示先升级 Server 再升级 Client。

4

客户端执行展示和安装动作

服务端返回 presentation 和 installer，客户端不拼业务规则。

App Store 构建注意：

兼容检查不能被 inAppUpdatesEnabled 禁用。商店渠道只禁用应用内安装，不禁用版本上报和兼容判断。

测试与验收

Node.js 测试

  • Client/Server 完全一致返回 ok。
  • Client/Server 只有 patch 差异返回 recommended_client_update 或 recommended_server_update。
  • Client/Server 的 major.minor 不一致返回 required_client_update 或 required_server_update。
  • GitHub latest patch 更新返回可选 server-then-client 升级。
  • GitHub latest major.minor 更新返回强制 server-then-client 升级。
  • 旧版 check_update 请求保持旧响应。

Flutter 测试

  • 新响应模型解析正确。
  • required action 进入强制升级状态。
  • optional action 可关闭。
  • App Store 构建仍发送兼容检查字段。
  • Android installer 可用 mock MethodChannel 验证调用参数。
验收项 必须满足
兼容线不一致 客户端阻断主流程。
只有 patch 差异 客户端提示风险，并允许点“知道了”关闭。
GitHub 不可达 不影响本地兼容检查，不阻断匹配版本继续使用。
服务端 action 足以驱动客户端 UI，客户端不内置业务判断。
Android 完成确认升级、下载、调起系统安装器闭环。
生产数据 新增测试不得访问 server/data/clawke.db。
