Clawke Client 设计评审

多会话流式运行态隔离设计

右侧聊天区保持一个 ChatScreen viewport。接收层允许多个会话同时流式接收，但每个会话的正文、Thinking、等待状态、工具状态和缓冲区都按 conversationId 隔离。当前 viewport 只订阅当前会话。

问题定位

当前闪烁的根因不是渲染细节，而是接收层和展示层共用全局单槽 streaming state。后台会话 delta 到达时，会覆盖当前会话状态，并触发当前聊天页重建。
现在的问题

全局 streamingMessageProvider / streamingThinkingProvider 只能保存一条流。两个会话交错 delta 会互相覆盖。

目标体验

后台会话继续累计流式内容；当前聊天区不闪。用户切过去时，看到已经累计到的位置并继续流式。

硬约束

  • 禁止 text_delta 和 thinking_delta 写数据库。
  • 禁止 每个会话保留一个常驻隐藏 ChatScreen。
  • 固定 左侧会话列表 preview/time 只在 text_done 后一次性更新。
  • 固定 后台会话流式接收不能触发当前聊天区闪烁。
  • 固定 切到后台会话时，展示该会话已累计到的位置。

架构原则

一个 ChatScreen viewport 只负责展示当前 selectedConversationId
+
按会话隔离的轻量运行态 stream / thinking / waiting / tool / buffer / timer

切换会话时，viewport 绑定到另一个 conversationId 的状态。系统不创建多个隐藏聊天页，也不把 token 流写入 DB。

运行态模型

Map<String, ConversationRuntimeState>
字段 用途 隔离要求
streamingTextMessage 当前会话正在显示的流式正文 按 conversationId
streamingThinkingMessage 当前会话正在显示的 Thinking 按 conversationId
waitingForReply 发送后、首个 delta 前的等待状态 按 conversationId
activeTool 工具调用中的展示状态 按 conversationId
textBuffer / thinkingBuffer 高频 delta 的内存缓冲区 按 conversationId
textFlushTimer / thinkingFlushTimer 节流刷新定时器 按 conversationId

接收流程

text_delta

只进内存

读取 conversationId，append 到该会话 text buffer，刷新该会话 streaming text。不写 DB，不更新左侧列表。

thinking_delta

只进内存

读取 conversationId，append 到该会话 thinking buffer，刷新该会话 Thinking。不写 DB，不更新左侧列表。

text_done

一次性持久化

读取该会话 runtime state，将最终正文和 Thinking 写入 DB，更新 preview/time，清理该会话运行态。

1
delta 到达

从消息中拿到 conversationId。

2
定位运行态

更新 runtimeState[conversationId]。

3
按会话通知

只通知该会话的订阅者。

4
done 后落库

最终消息写 DB，列表一次性更新。

展示流程

selectedConversationId -> ConversationRuntimeState?
当前会话

展示正文、Thinking、等待状态、工具状态和停止按钮。只有当前会话的运行态变化会刷新右侧聊天区。

后台会话

继续在内存中累计流式内容。不会刷新当前右侧聊天区，不会触发 preview/time 跳动。

切到后台会话

立即显示该会话已累计内容，然后继续 append 后续 delta。

切回原会话

原会话运行态仍在，不会被其他会话清掉或 finalize。

不采用的方案

不做

delta 写 DB

token 高频到达会造成大量 IO、Drift watch 重算、列表刷新和移动端性能压力。最终 text_done 已足够完成持久化。

不做

每会话常驻 ChatScreen

隐藏页面也会占用 controller、ListView、Widget 树和 DB watcher，还可能在后台继续 rebuild。会话多时内存和 CPU 线性增长。

第一阶段范围

任务 说明
流式正文按会话隔离 streamingMessageProvider 从单值改为按 conversationId 读取。
Thinking 按会话隔离 streamingThinkingProvider 从单值改为按 conversationId 读取。
Waiting / Tool 按会话隔离 等待回复和工具执行状态不再是全局单槽。
Buffer / Timer 按会话隔离 移除跨会话共享的文本缓冲、Thinking 缓冲和 flush timer。
ChatScreen 订阅当前会话 右侧聊天区只 watch 当前 conversationId 的运行态。
补充测试 覆盖两个会话交错 delta、切换会话继续显示累计内容、done 后才写 DB。

TDD 与 E2E 策略

这次必须先复现 bug，再改代码。先写失败用例，确认当前实现会失败，并且失败原因是多会话流式状态串扰。
RED

Provider / Widget 先精确复现

模拟 A、B 两个会话交错收到 delta，断言 A 的内容仍是 A 自己的累计内容，B 也是 B 自己的累计内容，且任一会话都不能被另一会话 finalize 或清空。

A: text_delta "A1"
B: text_delta "B1"
A: text_delta "A2"

expect(A.streamingText == "A1A2")
expect(B.streamingText == "B1")
E2E

再覆盖用户可见路径

创建会话 A 和 B，让 Mock Gateway 对两个 conversation_id 慢速交错流式回复。测试在 A/B 之间切换，验证已累计内容、当前页不被后台污染、text_done 前列表不跳动。

create A -> stream A slowly
create B -> stream B slowly
switch A/B
assert current chat only shows current conversation
assert preview/time updates only after text_done

为什么不是只靠 E2E

E2E 必须有，因为这个 bug 是用户可见闪烁和切换体验问题。但 E2E 粒度大、运行慢、定位不够精确，所以需要 provider/widget 测试先锁住根因，再用 E2E 做端到端验收。

顺序 动作 通过条件
1 新增 provider/widget 失败用例 当前代码 RED，失败点是全局单槽串扰
2 新增 UI E2E 失败用例 能复现两个会话交错流式的用户路径问题
3 实现按会话隔离运行态 不写 delta 到 DB，不引入多个常驻 ChatScreen
4 重跑 provider/widget 测试 多会话运行态互不覆盖
5 重跑 UI E2E 切换会话时能看到各自累计内容，当前页不闪烁
6 重跑既有聊天/流式回归 断连恢复、Thinking、停止按钮不回归

暂不做

  • 不做每个会话独立 ChatScreen 常驻。
  • 不做 delta 写 DB。
  • 不扩大到草稿和滚动位置持久化。
  • 不改服务端重试机制和 Gateway 协议。

验收标准

  • 两个会话同时接收流式内容时，当前聊天区不闪烁。
  • A 会话流式中切到 B，会显示 B 已累计的流式内容。
  • B 后台继续流式时，不影响 A 的右侧聊天区。
  • text_done 前左侧会话 preview/time 不跳动。
  • text_done 后消息写入 DB，左侧会话列表一次性更新。
  • Flutter 单元测试覆盖多会话交错流式场景。
  • UI E2E 覆盖两个会话交错流式、切换会话、后台流式不污染当前会话。
